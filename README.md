# Real-time Insights

Живая карта знаний разговора. Экран слушает микрофон, показывает речь текстом почти
в реальном времени и одновременно собирает из разговора базу инсайтов в виде
облачков-карточек: факты, вопросы (и ответы на них), предпочтения, решения.
Карточки не плодятся на каждую реплику — новая информация в первую очередь
дополняет уже существующую карточку (`update`), и только если подходящей карточки
нет — создаётся новая (`create`). Незаконченная мысль ничего не создаёт.

Это не чат, не субтитры и не саммари «после встречи» — карта растёт по ходу разговора.

## Стек

- `web/` — Vite + React + TypeScript, без Next.js. Состояние — Zustand. Стили — обычный CSS.
- `server/` — Node.js + TypeScript + Fastify + `@fastify/websocket` (поверх `ws`), один процесс.
- Контракты (WS-сообщения, операции LLM) валидируются Zod и на сервере, и на клиенте.
- Сессия живёт в памяти процесса — БД нет, персистентности между перезапусками нет.

## Важно: Whisper и LLM — не наши сервисы

Этот проект **не разворачивает** ни Whisper, ни LLM — сервер обращается к ним по сети,
как к обычным HTTP API. Whisper не умеет настоящий streaming — сервер сам режет речь на
перекрывающиеся окна для interim-текста и посылает финальный чистый запрос на паузе
(подробности ниже, в разделе «Как устроен STT»).

По умолчанию `.env.example` настроен на **облачный Whisper** (OpenAI-совместимый
`/v1/audio/transcriptions`, например через routerai.ru или напрямую OpenAI) — это
проверенный на практике вариант: self-hosted Whisper на слабой/шаренной VPS регулярно
не тянет CPU-инференс и падает под нагрузкой соседних процессов на том же хосте.
Свой self-hosted Whisper по-прежнему поддерживается (протоколы `asr`/`custom`, см.
таблицу ниже) — просто это уже не единственный и не обязательный путь.

LLM для извлечения инсайтов — любой OpenAI-совместимый Chat Completions API
(OpenAI, локальный сервер с таким же контрактом, прокси и т.п.).

## Настройка

```bash
cp .env.example .env
```

Заполни `.env`:

```ini
PORT=8000

# --- Whisper (по умолчанию облако, см. таблицу протоколов ниже) ---
WHISPER_BASE_URL=https://routerai.ru/api
WHISPER_API_KEY=                            # ключ провайдера (или пусто для self-hosted без авторизации)
WHISPER_MODEL=openai/whisper-large-v3-turbo # только для openai/asr-провайдеров с выбором модели
WHISPER_PROTOCOL=openai                     # openai | asr | custom, см. ниже
WHISPER_FIELD_NAME=file                     # только для protocol=custom
WHISPER_TIMEOUT_MS=20000

# Курс для счётчика расходов (₽) в правом нижнем углу UI
USD_TO_RUB_RATE=80

# --- LLM (OpenAI-совместимый Chat Completions) ---
LLM_BASE_URL=...
LLM_API_KEY=...
LLM_MODEL=...
LLM_TIMEOUT_MS=25000
```

### `WHISPER_PROTOCOL`

Сервер умеет говорить с Whisper тремя способами:

| Протокол | Куда стучимся | Поля multipart |
| --- | --- | --- |
| `openai` | `POST {WHISPER_BASE_URL}/v1/audio/transcriptions` | `file`, `model?`, `language=ru`, `response_format=json` |
| `asr` | `POST {WHISPER_BASE_URL}/asr` (как `openai-whisper-asr-webservice`) | `audio_file`, `language=ru`, `output=json` |
| `custom` | `POST {WHISPER_BASE_URL}` — сам URL уже полный адрес эндпоинта | `{WHISPER_FIELD_NAME}` (по умолчанию `file`), `language=ru` |

`custom` — для случаев, когда у тебя свой самописный API (например,
FastAPI-обёртка над `faster-whisper` с роутом вроде `/transcribe`, у которого
единственное multipart-поле — `file`). Ответ Whisper разбирается гибко: сервер
ищет текст в полях `text` / `transcript` / `transcription` / `result` в JSON-ответе,
либо принимает сырую строку.

Health-check: при старте и периодически во время записи сервер дёргает
`{origin}/health` (или сам `WHISPER_BASE_URL`, если `/health` недоступен).
Если Whisper не отвечает — кнопка записи в UI задизейблена, статус-бар
показывает «Whisper недоступен», запись вслепую не стартует.

### Счётчик расходов

В правом нижнем углу экрана — счётчик суммарных затрат за сессию в рублях. Если
провайдер Whisper/LLM отдаёт `usage.cost` в ответе API (так делает routerai, и
скорее всего большинство агрегаторов), сервер суммирует эти значения (в USD) и
переводит в рубли по фиксированному курсу `USD_TO_RUB_RATE`. Для self-hosted
Whisper/LLM без такого поля счётчик просто не растёт от них (стоимость = 0) —
это не подмена реального биллинга, а лёгкая прикидка по тому, что реально
возвращает провайдер.


Один `npm run dev` в корне поднимает и `server` (порт из `PORT`, по умолчанию 8000),
и `web` (Vite dev-сервер, порт 5173, с прокси `/api` и `/ws` на сервер). Открой
`http://localhost:5173`.

```bash
npm run dev:server
npm run dev:web
```

## Как устроен STT (Whisper-адаптер)

Whisper не умеет streaming, поэтому `WhisperSttProvider` строит псевдо-стриминг
поверх обычных HTTP-запросов:

1. Браузер захватывает микрофон (`getUserMedia`) и через `AudioWorklet` отдаёт
   PCM16 mono 16kHz чанками по ~150мс на сервер по WebSocket (бинарные фреймы).
2. Сервер гонит эти чанки через простой VAD по RMS-энергии сигнала: речь копится,
   пауза 600-900мс = граница реплики (utterance).
3. Пока человек говорит, каждые ~3.5с сервер шлёт в Whisper скользящее окно
   аудио (с overlap ~650мс с предыдущим окном) — это **interim**. Тексты соседних
   окон склеиваются по совпадающему хвосту/началу (`stitchText` в
   `server/src/stt/windowing.ts`), чтобы не дублировать слова на стыках.
   Interim идёт только в ленту транскрипта, в движок инсайтов не попадает.
4. На паузе сервер шлёт **весь** накопленный utterance в Whisper ещё раз —
   это **final**. Перед отправкой обрезается хвостовая тишина (с небольшим
   запасом), чтобы Whisper не начинал галлюцинировать на пустом аудио.
5. Перед каждым запросом в Whisper (и interim, и final) кусок аудио дополнительно
   проверяется настоящей нейросетевой VAD — [Silero](https://github.com/snakers4/silero-vad)
   через `@ricky0123/vad-node` (`server/src/audio/sileroVad.ts`). RMS-детектор из
   пункта 2 хорош для определения границ реплики (когда началась и закончилась
   пауза), но громкий не-речевой шум он засчитывает как «речь», потому что смотрит
   только на громкость. Silero действительно понимает, есть ли в куске речь, и если
   нет — кусок в Whisper вообще не уходит. Если сам Silero почему-то падает, пайплайн
   не блокируется (fail-open: кусок всё равно уходит в Whisper).
6. То, что всё же дошло до Whisper и было распознано, дополнительно фильтруется по
   тексту (`isLikelyHallucination` в `server/src/stt/windowing.ts`) — вторая линия
   защиты на случай типовых Whisper-галлюцинаций на грани тишины/шума («Продолжение
   следует...», подписи вроде «весёлая музыка» / «лай собак», титры субтитров, пустой
   ответ, повтор одного символа, ответ без единой буквы). Список коротких фраз-подписей
   взят из живого замера на 13ч шумовых записей (ru, whisper-large-v2):
   https://gist.github.com/waveletdeboshir/8bf52f04bf78018194f25b2390c08309
7. Все запросы к Whisper для одной сессии идут строго последовательно (нет
   гонки interim/final), event loop не блокируется — запросы асинхронные.

Диаризации через Whisper нет. Спикер определяется грубой эвристикой: пауза
дольше ~4с — гипотеза, что говорит другой человек (переключение Speaker 1 /
Speaker 2). Имя спикера можно переименовать вручную кликом по имени на карточке.

## Движок инсайтов

На каждый **final** (с debounce 1.5-3с и не более одного запроса к LLM в полёте
на сессию — новые final, пришедшие во время ожидания ответа, подхватываются
следующим тиком) сервер зовёт LLM с:

- последними 3-8 final-репликами,
- текущими карточками сессии (без длинных evidence — только суть),
- жёстким системным промптом (`server/src/insights/systemPrompt.ts`), который
  запрещает выдумывать факты и требует вернуть `{"ops":[]}`, если мысль не
  закончена.

LLM возвращает 0-3 операции (`create` / `update` / `answer` / `merge` / `discard`).
Сервер валидирует и фильтрует их (`server/src/insights/applyOps.ts`) прежде чем
применять и рассылать `insight_event`:

- неизвестный `insightId` → игнор;
- `create` с `confidence < 0.55` → игнор;
- `create`-дубль по нормализованному title/body → превращается в `update`
  существующей карточки вместо новой;
- больше 3 операций за тик → лишнее отбрасывается;
- максимум 40 карточек на сессию — дальше только `update` / `answer` / `merge`.

Если запрос к LLM падает по таймауту/ошибке, движок делает один повторный тик (через тот
же debounce), а не теряет реплику навсегда молча — но и не долбит упавший LLM бесконечно.

Reasoning-модели (DeepSeek R1-подобные и т.п.) тратят много токенов на "размышления" и
могут отвечать заметно дольше 10-15 секунд даже на короткий батч из 2-3 реплик — это
проверено вживую на `deepseek/deepseek-v4-flash-0731` через routerai.ru. Если видишь
частые таймауты в статус-баре (LLM: down), подними `LLM_TIMEOUT_MS` в `.env`.

Для отладки самих операций LLM (без микрофона, поверх симулятора) можно поднять сервер с
`DEBUG_INSIGHTS=1` — в консоли сервера будет виден promt-контекст и сырой `ops`-ответ
модели на каждый тик.

## Симулятор реплик (dev-режим, без микрофона)

В статус-баре есть кнопка `dev` — открывает панель, где можно:

- вписать произвольный текст и отправить его как `final`-реплику (в обход
  микрофона и Whisper);
- прогнать три готовых сценария приёмки одной кнопкой.

### Сценарий A — вопрос-ответ

1. «А какая погода будет завтра на улице?» → создаётся карточка-вопрос.
2. «Ну короче, не знаю, подожди» → без изменений (`ops: []`, мысль не закончена).
3. «Завтра на улице будет 17 градусов» → та же карточка получает `op: answer`,
   становится `qa`, новое облако не появляется.

### Сценарий B — накопление одного факта

1. «Я очень люблю собак» → создаётся карточка-preference (Speaker 1).
2. «Лучшие собаки — это доберманы» → `update` той же карточки.
3. «У меня, кстати, есть доберман» → снова `update`, карточка всё ещё одна.

Итог: одна карточка, а не три, — LLM видит текущие карточки как контекст и не
плодит дубли.

### Сценарий C — шум

«ну», «короче», «подожди», смех — ни одной карточки не создаётся.

Для проверки на реальном Whisper (без симулятора) просто говори в микрофон на
русском — реплики появятся в ленте транскрипта (interim серым, final белым),
инсайты — в виде облаков на холсте.

## Docker Compose

Только после того, как `npm run dev` уже работает локально:

```bash
docker compose up --build
```

Поднимет `server` (порт 8000, конфиг из `.env`) и `web` (порт 8100, статическая
сборка на встроенном Node-сервере без nginx). Веб-контейнер не проксирует
запросы к серверу — браузер обращается к серверу напрямую, поэтому при сборке
веба нужен `VITE_API_BASE_URL` (адрес сервера, доступный из браузера, по
умолчанию `http://localhost:8000`, задаётся в `.env`).

### Деплой под путём за реверс-прокси (`docker-compose.prod.yml`)

Для деплоя на общем хосте под конкретным путём на существующем домене (а не
отдельным поддоменом) — например `https://example.com/realtimeinsights` рядом
с другими сервисами за Traefik — есть отдельный оверлей `docker-compose.prod.yml`:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Он добавляет Traefik-лейблы (роутер с `PathPrefix` + `StripPrefix`, чтобы
приложение внутри контейнеров ничего не знало о префиксе пути) и собирает
фронт с `VITE_BASE_PATH=/realtimeinsights/`, чтобы ассеты и WebSocket-подключение
знали, что живут не в корне домена. Хост, путь и имя Traefik-сети (`root_default`)
в файле захардкожены под конкретный сервер — при переносе на другой хост поменяй
`Host()` и имя сети под свой Traefik. Контейнеры не публикуют порты наружу —
достаточно быть в одной docker-сети с Traefik.

## Ограничения v0

- Нет реальной диаризации — только эвристика по паузам, спикеров можно
  переименовать вручную.
- Нет сохранения между запусками процесса — сессия только в памяти.
- Один микрофон, одна сессия на процесс.
- Позиции карточек на холсте фронт назначает сам (простая спираль с джиттером),
  сервер о координатах ничего не знает, кроме факта, что карточка существует.
- REST — минимальный: `GET /health` и `GET /api/session/:id` (снимок сессии для
  отладки), никакого CRUD сверху.
